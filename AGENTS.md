# Inbox

A desktop app (Electron; macOS, Linux, Windows) that turns a GitHub review load into one queue. It's early and the owner is still finding what they want: keep changes small and easy to undo, and prefer plain code over new abstractions.

What each page does and says: [docs/ui.md](docs/ui.md). Behaviour and the API: [docs/api.md](docs/api.md). Look and layout: [docs/visual.md](docs/visual.md).

## Product principle

- **One list of what needs the owner.** The Inbox has three sections, Urgent, Standard and FYI, placed and ordered by `src/urgency.ts` (criteria, a score out of 10, thresholds). Each row is one line, says why it's there, and has at most one call to action. Everything else is sorted away by rules and the judge weighing them.
- **State lives in the desk; clients only render.** `src/desk.ts` decides what's on the queue, its order and what notifies. The window, tray, CLI, MCP and notifications all show the same state.
- **Never hold back the action an item is there for.** Anything on the Inbox can be acted on from the desk.
- **Automate before adding pages.** New behaviour becomes a rule or a setting, not a new page.
- **Mouse first.** Every action is a click named in words: a button, a link or a row's right-click menu. Only platform keys work (Esc, ⌘↵, ⌘S, Tab, ↓ and ↑ on a list, ⌘1 to ⌘4, ⌘[ and ⌘]), and the window names a key only in its button's tooltip.
- **Colour only for information.** A calm palette. Colour marks CI failing, a conflict, changes requested, an AI review's risk, and calls to action (the accent). Lists are tables, sentence case, no boxed chips.
- **Problems with the system are bubbles.** The desk offline, a failed sync, the agent logged out, broken rules or a refused action show as a bubble at the window's bottom right. What belongs to an item (its CI, its AI review failing) stays on the item.
- **Look before calling a UI change done.** Run `npm run shots` and look at `.shots/` in light and dark, each theme and each size (`-- --only queue,later` shoots just those). [docs/visual.md → Checking a design change](docs/visual.md#checking-a-design-change) says what to look at; the `design-check` workflow runs it.

Pages, top to bottom in the sidebar: Inbox, Blocked, then Merging and the Archive; Ask your agent and Settings in the footer. **Hand off for merge** moves the owner's PR to Merging, where the coordinator (a background agent session the desk starts and wakes; the window calls it "your agent") gets it merged or hands it back. See [README → Coordinator](README.md#coordinator).

## Run

```bash
npm run app        # the desktop app from the repo
npm run app:dev    # the app running from this checkout; restarts on electron/ changes
npm run dev        # server --watch + Vite in a browser at :5173
npm test           # node:test, no network
npm run check      # everything CI runs: prettier, oxlint (type-aware), stylelint, tsc, knip, tests
npm run format     # prettier --write
```

`DESK_HOME` and `DESK_PORT` point any of these at a scratch home and port (default `~/.inbox` on 47823). `DESK_SENTRY=0` keeps a run out of Sentry.

### Run from a checkout

Settings → This device → Run from a checkout (`app.source`, or `DESK_SOURCE`) makes the packaged app run the desk and UI from a checkout such as `~/code/review-desk`. A merge to main then goes live without a restart, so keep main startable.

- A change under `src/` restarts only the desk (`node --watch`); the window reconnects on the same view.
- A change under `web/` hot-reloads (Vite). `http://localhost:47823` serves the same live UI (`DESK_UI_ORIGIN`).
- A change under `electron/` needs a rebuilt app (`npm run dist:mac`).
- Without a checkout, the desk serves the last `npm run build` from `web/dist`.
- Logs from both processes: `~/.inbox/live.log`. A desk that fails to start shows its last lines in the window and retries on the next change or `npm install`.
- It needs Node 22.18+ on the login shell's PATH (or in nvm, Volta, mise, asdf or fnm). Until it finds node and `node_modules`, the window says what's missing and checks again every 15 seconds.

## Rules

- **Commits.** Small commits straight on main: no branches or pull requests (the owner is effectively the only contributor). Each commit is one change that passes `npm run check`. Commit messages are one line: the owner's habit.
- **GitHub writes.** The desk writes to GitHub only through `src/github/write.ts`, and only on an explicit click in the UI. Its `ALLOWED` map is the complete list of mutations; adding one is a product decision, not a refactor.
  - Today's writes: Approve, Comment (PR or issue), a comment on a diff line, Reply in a conversation, Ready for review (and asking the picked reviewers), Ask reviewers, the row's Merge, and the More menu's close, reopen, convert to draft, merge, re-request review, remove me as a reviewer (the one REST write, `REST_ALLOWED`), request changes and close issue.
  - `Desk.actions()` decides which an item allows, by whose it is (`me.author`: yours, or a bot's PR opened for you; a bot's `via` line alone never counts). It refuses others with 409.
  - Nothing an agent can call (MCP, CLI) reaches the writer. The read client in `src/github/client.ts` refuses any `mutation`.
  - Hand off for merge, Back to desk, hand-backs and Ask your agent write nothing to GitHub.
  - ⌘↵ in a box sends it like its button; no key outside a box writes. Nothing asks for a second press.
  - Every write is logged. Tests use a fake writer; live checks stub it (`startServer({ writer })`) and never touch real PRs.
- **Settings stay findable and in sync.** A setting goes in the part someone would look for it under: a feature with its own name (Tailscale, GitHub) gets its own part, never a row inside another. A part's name is in `SETTINGS_PARTS` (`web/src/view.ts`) and, word for word, in `SECTIONS` (`src/settings.ts`); `docs/ui.md` (its "The core's" line and a heading each) and README's Settings line list the parts in sidebar order; shots read them from `SETTINGS_PARTS`. Rename a part with fastmod over every "Settings → …" path, and add an alias in `SETTINGS_ALIAS` for its old route. `web/test/settings-sync.test.ts` fails until all of them agree; don't loosen it to pass.
- **Errors are Effects** (`effect` 4.x). A function that can fail returns `Effect.Effect<A, E>` with a tagged error from `src/errors.ts`. No `throw`/`try`/`catch` for expected failures. Background work goes through `desk.runner.fork` (the window's through `runUi`). An unawaited promise is a lint error (`.oxlintrc.json` says where). Read [docs/effect.md](docs/effect.md) before touching error handling.
- **TypeScript runs directly** (type stripping): no enums, namespaces or parameter properties; relative imports end in `.ts`; type-only imports use `import type`.
- **Comments:** one line, only for a non-obvious why.
- **Tests** for logic changes, in `test/` or `web/test/`. Tests never run a real agent: they put a fake `claude`, `codex` or `opencode` in a temp dir (`DESK_CLAUDE`, `DESK_CODEX`, `DESK_OPENCODE`). `scripts/agents-e2e/` runs Codex and OpenCode for real in a container, by hand.
- **`npm run check` must pass** (the pre-push hook runs it; CI runs it on macOS, Linux and Windows). Fix findings, don't silence them. Use `// oxlint-disable-next-line <rule> -- <reason>` only where the rule is wrong for that line. Don't loosen `.oxlintrc.json` or the tsconfig flags.
- TypeScript 7 (the Go compiler) has no JS API, so typescript-eslint can't run; type-aware linting is oxlint + tsgolint.
